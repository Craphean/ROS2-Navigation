## 诊断并修复：仓库场景双机探索双双中断（ABORTED）

**现象**：12:59 那轮 warehouse 多机探索跑到 13:06 两车同时失效，协调器此后一直刷
`Action server not ready!`，任务静默挂死。`/tmp/tb3_multi_*.log` 因 15:26 重启被清空，
证据来自 `~/.ros/log/*.log`（ROS 节点日志跨重启保留）。

**根因链**（已用日志时间戳逐条对上）：
1. commit f3ada88「initial 3D dual exploration」把 3D 雷达原始点云（720×32≈23k 点、5 Hz）
   加进 **global_costmap 的 obstacle_layer**（`clearing: true` + `raytrace_max_range: 6.0`）。
2. 505×600 栅格上单次 `updateMap()` 要 0.6–0.9 s（`planner_server` 日志
   `Planner loop missed its desired rate of 2.0000 Hz ... Waited 0.7s for costmap update`，
   41 条/18 条），代价地图锁约 70% 时间被占。
3. `planner_server` 执行器被饿死 → `is_path_valid` 成片超时 → lifecycle bond 4 s 收不到心跳
   → `lifecycle_manager_nav2`：`CRITICAL FAILURE: SERVER planner_server IS DOWN`，把整栈 Nav2
   Deactivate + Cleanup（两车分别 13:06:09 / 13:06:38）。
4. 自动 re-bringup 失败：`collision_monitor` 第二次 configure 抛
   `parameter 'FootprintApproach.points' is not initialized`（nav2 1.5.2 的
   `declare_or_get_parameter<std::string>` 在「已声明但未初始化」时抛
   `ParameterUninitializedException`，而 `Polygon::getParameters` 只 catch
   `InvalidParameterValueException`）→ 两车都 `Failed to bring up all requested nodes. Aborting bringup.`

**修复**：
- `config/nav2_multirobot_slam_params.yaml`
  - global_costmap `obstacle_layer`：`observation_sources: scan`（移除 points）；scan 量程提到
    obstacle 5.0 / raytrace 5.5 补偿。
  - local_costmap `voxel_layer.points`：只保留 marking，`clearing: false`、`raytrace_max_range: 0.0`、
    `obstacle_max_range: 3.0`。
  - `collision_monitor.FootprintApproach`：显式写 `points`（同 FootprintStop），去掉 footprint_topic。
- `config/coordinator_params.yaml` + `scripts/multi_robot_coordinator.py`：新增 `_check_nav_stack`
  看门狗（`nav_outage_warn_period: 15.0`），导航栈掉线只报一次 + 定期提醒 + 恢复提示；
  `_dispatch_goal_locked` 不再每周期刷 `Action server not ready!`。
- `docs/3d_mapping_plan.md`：记录「points 不能进全局代价地图」的实测结论，以及需要桌面投影时
  应先降采样到 0.10 m。

**验证**：`nav2_collision_monitor` 单节点跑 configure→cleanup→configure：旧配置第二次必失败
（已复现原错误），新配置两次都成功。

**机器画像**：4 核 / 12 GB 的 VMware 虚拟机，跑 Gazebo + 2×(Nav2 全栈 + slam_toolbox + 点云桥) +
merge_pointclouds + octomap + 协调器，CPU 极易过载；调参时优先考虑降载。

## 第二轮补充：robot2"不动"其实是派发侧静默停摆（已修）

**澄清**：robot2 一直在正常工作到 16:29:51（最后一次导航成功 16:29:31），16:29:51 的
`Active goal ... has been cleared by exploration! Cancelling goal...` 是**正常取消**。它之后不再动，
是因为协调器**再也没给它派新目标**，而且一行日志都没打。

**证据**：
- 16:29:37 之后 `[Auction Winner]` / `Sending Nav2 goal` 完全消失（直到 16:31:55 手动中断）；
- `[3D] voxel index: 5764 columns (+0)` 连续出现 —— 地图早已停止增长，探索其实已经做完；
- 既没有 `Exploration converged`，也没有 `No remaining reachable frontiers`；
- 同期 `robot1` 的越界目标把 33.8 m 那个 frontier 拉黑后，剩下的候选都 >35 m，
  `global_roi_min: 0.05` + ROI 随距离衰减 → 全部被 `run_global_auction` 里的
  `if roi < min_roi: continue` 丢掉，函数 `break` 后**静默返回**。

**修复**（`multi_robot_coordinator.py`）：
- `run_auction` / `run_global_auction` 改为返回派发数量，并把成功的机器人写进 `dispatched`
  （之前全局竞价派发后 `dispatched` 仍为空，标记也是错的）；
- `run_global_auction` 记录 `_global_reject_info=(候选数, 最高被拒ROI)`，调用方据此打一条
  10 s 限流的 `[Dispatch] N global candidate(s) all rejected by the ROI gate...` **并回退到
  旧竞价 `run_auction`**（无硬 ROI 门槛），保证"有候选就一定有人去"；
- 整个派发块之后加"活度兜底"：`dispatch_allowed and available and not dispatched` 时
  重新取当前 IDLE 的车再跑一次 `run_auction`，并打 `[Dispatch] ... falling back`。
- 单测：ROI 通过→派发1；ROI 全拒→返回0且记录原因；兜底竞价→正常派出；派发失败→不计数。

## 第三轮：16:47 warehouse 运行 —— 三个症状同一个根因：octomap 0.02 m 树爆

**症状**：3D 打分约一半周期被跳过（voxel build 150–340 ms > budget 150）；`/octomap_binary`、
`/octomap_point_cloud_centers`、`/projected_map` 全部停发；最后两车都不动。

**根因链**：
1. `config/octomap_params.yaml` 用了 `resolution: 0.02`（设计文档 `docs/3d_mapping_plan.md` 写的是 0.05，
   实现跑偏了）。仓库探索 30 分钟后树涨到 **48,205,661 叶子**。
2. `OctomapServer::insertCloudCallback` 每次插入点云都调 `publishAll()`，它要**遍历整棵树**；
   一旦有订阅者（采样、RViz、saver）还要 `writeBinary` 序列化整棵 48M 节点的树。
   → 节点卡在序列化里，日志停在 "Writing 48205661 nodes to output stream"，
     `/octomap_point_cloud_centers` / `/projected_map` / `/octomap_binary` 全停。
3. 4 核 VM 被这棵树拖垮 → 17:54:18 `collision_monitor` 的 lifecycle bond 4 s 收不到心跳 →
   `CRITICAL FAILURE: SERVER collision_monitor IS DOWN` → robot1 Nav2 整栈被拆
   （拆到 "Deactivating collision_monitor" 就卡住，2.5 分钟没走完）。
4. 协调器的体素构建被 CPU 抢占，墙钟 150–340 ms（离线实测只要 ~30 ms），
   叠加原来的 bug：`skip_3d = 本周期耗时 > 150 ms`，而体素重建刚跑完、索引最新，
   等于专挑最该用 3D 的周期退化成 2D。

**修复**：
- `octomap_params.yaml`：resolution 0.02 → **0.10**（叶子 ≈1/125，48M → ≈0.4M）。
  实测新配置下 `/octomap_point_cloud_centers`、`/projected_map` 正常发布（之前 0 条）。
  3D 打分对分辨率基本不敏感：density 是"被观测列占比"、occupancy 在 8 voxels/列就饱和、
  height 是物理米数；0.10 m 竖墙每列仍有 ~19 个体素 ≥ `min_points_per_column: 3`。
- `nav2_multirobot_slam_params.yaml`：新增 `lifecycle_manager_nav2.bond_timeout: 15.0`
  （nav2_bringup 没有暴露该 launch arg，只能走 yaml；参数名已从 libnav2_lifecycle_manager_core.so 确认）。
- `multi_robot_coordinator.py`：`skip_3d = not self._index_available(now)`，
  只有索引缺失/过期才退化为 2D；warning 措辞改成"CPU-bound，但仍用这份新索引打分"。
- 上一轮的调度兜底本轮生效：日志出现 `[Dispatch] 7 global candidate(s) all rejected by the ROI
  gate (best ROI 0.014 < min_roi 0.050); using the utility auction instead.` 并正常派出。

**运维提醒**：探索过程中不要订阅 `/octomap_binary`（有订阅者就每次地图变化 writeBinary 整棵树）；
存档用 octomap_saver 一次性做；想要细粒度 3D 档案就从 merge 的原始点云存 PCD，别把 octomap 调回 0.02。

## 存档工具升级：save_cloud_pcd.py 支持从原始点云累积存 PCD

**背景**：`/points_merged`（merge_pointclouds）是**每帧合并**，不是累积地图；单帧只有两车各一帧的薄片。
要拿整图必须累积，而原实现的 `--accumulate` 是把每帧原始消息塞进 list（≈21 GB/h），长时间必 OOM。
另外实测：在这个脚本的 `rclpy.spin_once` 循环里按 Ctrl-C，rclpy 的信号处理会卡在 shutdown，
最终被 SIGKILL（timeout -k 验证 exit=137），所以"Ctrl-C 保存"不可靠。

**改动**（`scripts/save_cloud_pcd.py`）：
- `--accumulate` 改为**增量体素哈希**（帧内先 np.unique 去重，再折进 dict），内存只随唯一体素数增长；
  `--voxel-size` 在累积模式默认 0.05。
- 新增 `--checkpoint-sec`（默认 60）：累积期间定期重写输出，被杀也留得下可用文件。
- 新增 `--binary`：二进制 PCD（12 B/点，比 ASCII 快约 50 倍），`write_pcd` 支持两种格式。
- `_safe_log` 兜底：ROS context 已关闭时改用 stderr，避免日志调用把保存流程打断。
- 测试：假 publisher 造 20k 点/帧、每帧平移；快照=20000 点，累积 7 s=390692 点，二进制文件 4.69 MB，
  头部 POINTS 与 frombuffer 解析条数一致。

**用法**：`--topic /points_merged --accumulate 3600 --voxel-size 0.05 --binary --checkpoint-sec 60`。
